# 露营小助手 · Web → 微信小程序迁移方案

> 生成日期：2026-06-10 ｜ 基于 dev 分支 `92728cc`
> 本文档是**纯方案设计**，未修改任何代码、未执行任何 SQL。
> 所有涉及数据库与身份体系的内容均为草案，需评审确认后才能进入实施。

---

## 0. 结论先行（TL;DR）

| 决策点 | 推荐 | 一句话理由 |
|--------|------|-----------|
| 形态 | **原生小程序（Taro + React）**，不做 web-view 套壳 | 个人主体小程序**不允许使用 web-view 组件**；即使企业主体，业务域名也需 ICP 备案 |
| 后端 | **保留 Supabase 作为唯一数据源，小程序经微信云函数代理访问** | 小程序 `wx.request` 合法域名必须 ICP 备案，`supabase.co` 无法备案、`gogocamping.xyz`（Vercel）同样无法备案；而 `wx.cloud.callFunction` 不受域名白名单限制，云函数出网调 Supabase 即可 |
| 实时同步 | 小程序端降级为**前台轮询**（建议 5s）+ 下拉刷新 | 云函数代理模式下拿不到 Supabase Realtime 推送；现有 `updatedAt` 比较合并模型天然兼容轮询 |
| 登录 | 计划功能**保持匿名**（房间码即权限，与 Web 一致）；装备大本营接微信静默登录，**必须先落地 `profiles + user_identities`** | CLAUDE.md 铁律：禁止把 openid 写入 `equipment_items.user_id`，禁止在身份映射层缺失时上线任何多登录方式 |
| Web 端 | **保持现状，继续作为生产主入口**，迁移期间零改动（除 P0 bug 修复） | 两端共享同一 `plans` 表，房间码跨端通用 |

**核心收益**：小程序端「扫小程序码进房间」「微信原生分享卡片」是这个产品在微信生态里最自然的形态，比现在「复制房间码 → 打开浏览器 → 手输」的链路短两步。

## 1. 硬约束盘点（决定技术路线的前提）

### 1.1 微信平台约束

| 约束 | 影响 |
|------|------|
| `wx.request` / `wx.connectSocket` 的目标域名必须 **https + ICP 备案 + 在小程序后台白名单** | `*.supabase.co` 是境外域名无 ICP 备案，**小程序无法直连 Supabase**（REST 和 Realtime WebSocket 都不行） |
| `web-view` 组件**仅企业主体可用**，且业务域名同样要备案 | 若当前是个人开发者，套壳路线直接不可行；即使可行，套壳体验（无原生分享/登录）也不值得做 |
| 个人主体可选类目有限 | 「工具 > 效率」类目对个人开放，本产品适配；涉及 UGC 文本（计划名/物资名等多人可见内容）按规范应接 `msgSecCheck` 内容安全检查 |
| 无 `localStorage` / `crypto.randomUUID` / DOM / `navigator.clipboard` / `<canvas>` DOM API | 需要适配层，详见 §4 功能映射表 |
| 小程序包体积主包 ≤ 2MB | 本项目无重依赖（仅 supabase-js，且小程序端不引入它），无压力 |

### 1.2 项目自身约束（CLAUDE.md / PROJECT_STATUS.md）

1. `plans` 表及其 RLS **绝对不动**——代理层只能使用与 Web 完全相同的 anon 访问方式。
2. 微信登录的**前置任务**是 `profiles + user_identities` 设计评审通过（本文 §5 即为该草案）。
3. 计划功能必须在未登录状态下完整可用——小程序端同样遵守：打开即用，登录只为装备大本营。
4. 数据结构永久兼容——小程序端必须复用同一份 `migratePlan`，不允许出现第二套兼容逻辑。

## 2. 形态选型对比

| 方案 | 说明 | 结论 |
|------|------|------|
| A. web-view 套壳 | 小程序内嵌现有网页 | ❌ 个人主体不可用；企业主体也需备案域名；无原生分享/扫码/登录，体验是「套壳浏览器」 |
| B. **Taro（React 语法）原生重建** | 同一套 React + TS 心智，逻辑层直接复用 | ✅ **推荐**。`types.ts` / `calculateSettlement` / `migratePlan` 等纯 TS 100% 复用；UI 层语义相近（View/Text 替代 div/span），inline style 写法基本保留 |
| C. uni-app（Vue） | 换框架 | ❌ 团队心智是 React，无额外收益 |
| D. 原生 WXML/WXSS | 全手写 | ❌ 逻辑层无法共享，长期双倍维护成本最高 |
| E. 后端整体迁微信云开发（CloudBase） | 抛弃 Supabase | ❌ 现阶段不做：需迁移生产数据、Web 端同步重写，违反「稳定优先」。仅当 §7 风险 R2（跨境延迟）实测不可接受时再评估 |

```

│ localStorage (store.ts)         │      │ wx.storage 适配版 store           │
│ sync.ts ──直连──┐               │      │ planApi ──wx.cloud.callFunction──┐│
└─────────────────┼───────────────┘      └──────────────────────────────────┼┘
                  │                                                          │
                  │                      ┌─ 微信云函数（Node.js，新建）──────┤
                  │                      │ plan-proxy：CRUD plans（anon key）│
                  │                      │ wx-auth：code2Session + 身份映射  │
                  │                      │ equipment-proxy：装备 CRUD        │
                  ▼                      └───────────────┬──────────────────┘
            ┌─ Supabase（唯一数据源，表结构按规范扩展）──▼──────────────────┐
            │ plans（不动） equipment_items（不动）                          │
            │ profiles / user_identities（新增，§5 草案，评审后才建）        │
            └────────────────────────────────────────────────────────────────┘
```

### 3.1 共享逻辑包

建议把纯逻辑收敛为一个可被两端引用的目录（monorepo 子包或直接 `src/core/` 平移）：

| 模块 | 复用度 | 说明 |
|------|--------|------|
| `types.ts`（含 `calculateSettlement`、`expenseIncludesFamily`） | **100%** | 零修改。这是产品的核心资产 |
| `store.ts` 中 `migratePlan` / `duplicatePlan` | **100%**（需先修复审阅文档 A1/A2） | 零修改 |
| `store.ts` 中 `generateId` | 需适配 | 小程序无 `crypto.randomUUID`，提供 fallback（如 `wx.getRandomValues` 或时间戳+随机数 UUID v4 实现） |
| `store.ts` 中 localStorage 读写 | 接口复用，实现替换 | 抽 `StorageAdapter` 接口：Web 用 localStorage，小程序用 `wx.setStorageSync`（key 沿用 `camping-plans-v1`，便于心智统一） |
| `sync.ts` | 接口复用，实现替换 | 函数签名（`createPlanInCloud` / `syncPlanToCloud` / `fetchPlanFromCloud` / `loadPlanByRoomCode`）已经是天然的后端契约，小程序版实现改为调云函数；`subscribeToPlan` 在小程序版替换为 `startPolling(planId, onUpdate)` |
| ShareTab 文案生成、菜单分组逻辑 | **100%** | 建议按审阅文档 C1 先提取为纯函数 |

### 3.2 云函数代理设计（plan-proxy）

- 持有 Supabase **anon key**（与 Web 端同一把，权限完全等价，不引入 service_role，从而天然遵守 plans 表现有 RLS 边界）。
- 暴露与 `sync.ts` 一一对应的 action：`create` / `upsert` / `fetchById` / `fetchByRoomCode`。
- 入参出参均为整个 plan JSON blob，**沿用 LWW + `updatedAt` 比较模型**，云函数不做任何业务逻辑，只做转发——保证两端行为一致。
- UGC 合规：在 `upsert` 入口对文本字段拼接后调用 `security.msgSecCheck`，违规则拒绝写入（仅小程序链路有此要求，Web 链路不变）。

### 3.3 实时同步降级策略

- 小程序前台：页面 `onShow` 立即 `fetchById` 一次（对应 Web 的 visibilitychange 回拉，行为对齐）；停留期间 5s 轮询，仅当云端 `updatedAt` 更新时应用（复用现有比较逻辑）。
- 本地编辑：与 Web 相同的 300ms 防抖 + `planRef` 模式平移到 Taro（React hooks 在 Taro 下可用）。
- 体验差异要明示：小程序端他人修改的可见延迟是秒级（≤5s），Web 端仍是 Realtime 毫秒级。对露营协作场景完全够用。

## 5. 身份体系设计草案（CLAUDE.md 前置任务）

> **以下 SQL 仅供评审，未执行。** 评审通过并由你明确确认后，才进入实施阶段。

### 5.1 设计目标

1. 邮箱账号（现有 Supabase Auth）与微信账号最终指向**同一个内部 `user_id`**，共享一份 `equipment_items` 数据。
2. `equipment_items.user_id` 语义不变，永远是 `auth.users.id`，**绝不写入 openid/unionid**。
3. 为未来公众号、手机号登录预留 provider 扩展位。

### 5.2 表结构草案

```sql
-- ⚠️ 草案，仅供评审，不执行

-- 统一用户档案：1:1 对应 auth.users
create table public.profiles (
  id          uuid primary key references auth.users(id) on delete cascade,
  nickname    text,
  avatar_url  text,
  created_at  timestamptz not null default now(),
  updated_at  timestamptz not null default now()
);
alter table public.profiles enable row level security;
create policy "profiles owner select" on public.profiles
  for select using (auth.uid() = id);
create policy "profiles owner update" on public.profiles
  for update using (auth.uid() = id);
-- insert 由服务端（云函数/触发器）完成，不开放客户端 insert

create trigger handle_profiles_updated_at
  before update on public.profiles
  for each row execute function ... ; -- 按规范使用独立命名的 trigger function

-- 外部登录身份 → 内部 user_id 映射
create table public.user_identities (
  id            uuid primary key default gen_random_uuid(),
  user_id       uuid not null references auth.users(id) on delete cascade,
  provider      text not null,   -- 'wechat_mini' | 'wechat_oa' | 'phone' ...
  provider_uid  text not null,   -- openid（按 provider 维度唯一）
  unionid       text,            -- 微信生态跨端合并的关键，可空
  created_at    timestamptz not null default now(),
  unique (provider, provider_uid)
);
create index user_identities_unionid_idx on public.user_identities (unionid)
  where unionid is not null;
alter table public.user_identities enable row level security;
-- 该表只允许服务端（云函数持有受限凭证）读写，客户端零直接访问
```

### 5.3 微信登录流程（全部在云函数 wx-auth 内完成）

```
小程序 wx.login() → code
  → 云函数 code2Session → openid (+ unionid)
  → 查 user_identities (provider='wechat_mini', provider_uid=openid)
      ├─ 命中 → 取 user_id
      └─ 未命中 → 用 Supabase Admin API 创建 auth user（无邮箱的占位账号）
                  → 写入 profiles + user_identities → 得到 user_id
  → 为该 user_id 签发 Supabase 兼容 JWT（或经 Admin API 换取 session）
  → 返回小程序，后续 equipment-proxy 请求携带该 token，
    Supabase RLS（auth.uid() = user_id）原样生效
```

### 5.4 邮箱账号与微信账号的合并

- 主动绑定：小程序内提供「绑定邮箱账号」入口——输入邮箱密码校验成功后，把微信 identity 的 `user_id` 改指向邮箱账号的 user_id，并迁移/合并占位账号的装备数据。
- **合并属于敏感数据操作**，实施前需单独出方案（含回滚步骤），按 CLAUDE.md 敏感表操作规范执行。
- V1 可以先不做合并入口，只保证表结构支持，不堵死路径。

### 5.5 红线自查

| CLAUDE.md 禁令 | 本方案如何遵守 |
|----------------|---------------|
| 禁止 openid 写入 `equipment_items.user_id` | openid 只存在于 `user_identities.provider_uid`；equipment 永远挂 auth user id |
| 禁止绕过 Supabase Auth 自建用户体系 | 微信用户也通过 Admin API 创建为正式 auth.users 记录 |
| 禁止身份绑定层缺失时上线多登录 | 实施顺序上 profiles/user_identities 建表先于任何登录代码（见 §6 Phase 1→5 依赖） |
| 不动 plans 表 | 计划功能全程匿名，不接触身份体系 |
