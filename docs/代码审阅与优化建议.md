## 总评

项目架构与产品复杂度匹配得很好，没有过度设计：

- **数据层干净**：`types.ts` 纯类型 + 纯函数（`calculateSettlement`），`store.ts` 只管 localStorage，`sync.ts` 只管云端，职责清晰。
- **同步逻辑成熟**：`planRef` 防 stale closure、300ms 防抖、Realtime 回调里的 `updatedAt` 时间戳比较、visibilitychange 回拉、online 自动重试——这套组合拳处理多设备协作的边界情况相当到位，**不建议动**。
- **数据兼容纪律好**：`migratePlan` 单一入口，新字段全部可选 + 默认值。

主要问题集中在两类：**① 少数数据正确性 bug**（集中在 `store.ts` 的复制/导入路径，不在主流程上，所以一直没暴露）；**② 跨文件的小规模重复代码**（可选清理项）。

## A. 正确性问题（建议尽快修，均为最小 diff）

### A1. 🔴 `duplicatePlan` 未重映射 `aaScope` → 副本的部分 AA 结算错误

**位置**：[store.ts:75-79](../src/store.ts)

`duplicatePlan` 重新生成所有 family id 并重映射了 `person.familyId`、`supply.assigneeId`、`expense.payerFamilyId`，**但漏了 `expense.aaScope`**（部分 AA 的 family id 列表）。

后果：复制一个含「部分 AA」花费的计划后，副本中该花费的 `aaScope` 指向已不存在的旧 family id → `expenseIncludesFamily` 对所有家庭返回 false → 该笔钱计入总额、垫付方拿到 credit，但**没有任何家庭分摊** → 各方 balance 总和不为零，转账方案算不平。

**最小修复**（约 4 行）：

```typescript
clone.expenses = clone.expenses.map(e => ({
  ...e,
  id: generateId(),
  payerFamilyId: familyIdMap[e.payerFamilyId] ?? e.payerFamilyId,
  aaScope: Array.isArray(e.aaScope)
    ? e.aaScope.map(fid => familyIdMap[fid] ?? fid)
    : e.aaScope,
}));
```

风险：极低。只影响复制路径，不碰存量数据。

### A2. 🔴 `importPlanFromJson` 未剥离 `roomCode` → 可能污染云端房间码

**位置**：[store.ts:134-147](../src/store.ts)

导出的 JSON 含 `roomCode` 字段。导入时 `plan.id` 被重新生成，但 `roomCode` 原样保留。之后 `openPlan` 用 `p.roomCode` 订阅并同步 → 首次编辑触发 `syncPlanToCloud` 的 **upsert**，向 `plans` 表插入一行**新 id + 旧 room_code** 的记录 → 同一 room_code 出现两行 → `loadPlanByRoomCode` 的 `.single()` 报错 → **所有人都无法再用这个房间码加入**。

对比：`duplicatePlan` 正确地做了 `delete clone.roomCode`，导入路径漏了。

**最小修复**（1 行）：在 `importPlanFromJson` 中 `delete plan.roomCode;`

风险：极低。这是生产环境真实可触发的数据污染路径，建议优先处理。

### A3. 🟡 `importPlanFromJson` 没有走 `migratePlan`

**位置**：[store.ts:134-147](../src/store.ts)

CLAUDE.md 规定「`migratePlan()` 是数据兼容的唯一入口」，但导入路径手工补了 `aaMode` / `menuItems` 两个字段，漏掉 `endDate`、`families.isSolo`、`supplies.needsAA`、`expenses.aaScope`、`people` 等。导入一份老版本导出的 JSON 时这些字段缺失。

目前没出事是因为 `loadPlans()` 读取时会再过一遍 `migratePlan`，**算是被动兜住了**。但建议导入时直接调用 `migratePlan(plan)` 替换手工补丁，消除两套补丁逻辑漂移的可能。

**最小修复**：`return migratePlan(plan)`，并删除手工 `aaMode`/`menuItems` 两行。风险极低。

### A4. 🟡 `deleteFamily` 留下悬挂引用，结算可能不平

**位置**：[OverviewTab.tsx:180-186](../src/pages/tabs/OverviewTab.tsx)

删除家庭时只校验「有成员则禁止」，**不检查物资和花费**。对比 `deleteSoloPerson`（209-212 行）会清理 supplies 和 expenses，两条删除路径行为不一致。

家庭被删后：
- 物资 `assigneeId` 悬挂 → UI 显示「未指定」，可接受；
- 花费 `payerFamilyId` 悬挂 → 归入「其他」分组，**但结算时**：金额计入 AA 总额并分摊给大家，垫付 credit 却没人拿到（payer 不在 map 里被跳过）→ 各方 balance 总和为负，转账方案不闭合。

**建议**（二选一，倾向前者）：
1. 删除家庭时与 `deleteSoloPerson` 对齐：同步清理/置空相关 supplies、删除相关 expenses（删除前用现有确认弹窗提示「该家庭有 N 笔花费将一并删除」）；
2. 或在 `calculateSettlement` 里跳过 payer 不存在的 expense（不计入 totalAmount）。

风险：低-中（涉及删除确认的交互文案，建议先确认产品预期）。

### A5. 🟢 `deleteSoloPerson` 未清理 `aaScope` 中的引用（边缘情况）

**位置**：[OverviewTab.tsx:204-213](../src/pages/tabs/OverviewTab.tsx)

删除独立参与者时，若某笔部分 AA 花费的 `aaScope` 里**只有**这个人，删除后 scope 为空 → 与 A1 同类的「有垫付无分摊」失衡。概率很低，可与 A4 一并处理：删除结算主体时把它从所有 `aaScope` 数组中移除，移除后若数组为空则视为 `'all'` 或删除该笔。

## D. 已知权衡，明确「不建议改」的部分

1. **整 blob 最后写入胜出（LWW）同步模型**：两人在 300ms 防抖窗口内同时编辑，后写者覆盖前者。对 2-6 家庭的协作规模，配合 `updatedAt` 比较 + Realtime 推送，实际冲突率很低，**改成 CRDT/字段级合并的复杂度完全不值得**。保持现状，仅在迁移文档中作为已知特性记录。
2. **`plans` 表 public RLS + 房间码即权限**：匿名协作的根基，CLAUDE.md 明令不动。房间码 6 位（32⁶ ≈ 10 亿）被枚举的风险通过 Supabase 默认限流缓解，可接受。
3. **inline style 体系**：虽然文件偏长，但配合 CSS 变量用得一致，没有样式冲突问题。全面改 CSS Modules/styled 属于大重构，禁止清单范围。
4. **App.tsx 的防抖 + planRef + 订阅生命周期**：是整个项目最精细的部分，注释完备，不要为任何「优雅」理由重写。
